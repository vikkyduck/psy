Прежний релиз ПСИ: 717793d83d21c424e0b62a268c857520aa515d8b.

Снимок фактической среды до обновления имеет SHA256 b610615ac5a579bfbfeda604218b9b09143c797bdaadb685893d1a3f35263a80 и включает 1314 файлов. Он дополняет ранние снимки, а не заменяет их. Содержимое приватных файлов не публикуется. Снимок среды зависимостей описывает committed_venv и реальный интерпретатор. Он не выдается за интроспекцию всех импортов старого работающего процесса.

Текст запроса, ответа и карты требований в технический экспорт не включается. Операционный порядок описан в [OBSERVABILITY.md](OBSERVABILITY.md).

Блокирующих содержательных ошибок ни в одной из пяти пар не найдено. Этот небольшой набор не доказал превосходство новой версии по качеству текста: старые ответы тоже прошли. Он подтвердил работоспособность новых механизмов на указанных задачах.

Обычные пары выполнялись в изолированном композиционном стенде на Python 3.12. Он загружал реальные модули и обращался к действующему провайдеру. После обнаружения отличия от Python рабочей службы стресс-тест памяти повторен на настоящем Python 3.14.7. Полный технический набор также выполнен на нем. Композиционный стенд не проверяет доставку Telegram и не воспроизводит прежнюю выборку истории из шести обменов. Эти свойства проверяются отдельными тестами базы и очереди.

## Сжатие истории и найденная ошибка

Первый стресс-тест остановился с context_compaction_invalid. Причиной было отсутствие токенизатора: резервная оценка по байтам UTF-8 слишком рано отклоняла русскую карту требований при искусственном бюджете 4096. Ошибка сохранена в протоколе и не засчитана как успешный ответ.

Установлен отдельный проверенный tiktoken 0.12.0 с кешем o200k_base и пакетами для ABI рабочего Python. Окружение Hermes не изменялось. Установка проверяет хеши пакетов и кеша, затем выполняет автономную проверку под пользователем службы. Получение пакетов во время ответа запрещено.

Повторный тест на Python 3.14.7:

- Исходная история: 20 сообщений.
- В карту свернуты 13 сообщений за четыре вызова модели.
- Подготовленный вход: 3631 токен при тестовом бюджете 4096.
- Всего семь модельных этапов, все с effort=max, без понижения.
- task_status=complete, все причины завершения completed.
- Сетевых нарушений и запросов к настоящему Telegram: 0.
- Продолжительность: 263,88 секунды.

Бюджет 4096 установлен только стендом для проверки сжатия. Это не рабочее ограничение. Серверный каталог выбранной модели сообщил окно 500000 токенов. Код резервирует одну пятую для ответа, рассуждения и служебных инструкций. Источник значения окна фиксируется в диагностике каждого ответа.

## Техническая приемка

До завершающих дополнений к аудиту полный набор на Linux и Python 3.14.7 прошел 344 проверки. Дополнения отдельно проверяют происхождение фактического токенизатора, сохранение исходной причины модельного сбоя при ошибке SQLite, аудит изображения и причины неопределенной доставки. Полный итоговый набор запускается CI для точного коммита PR.

Тесты воспроизводят терминальные и временные сбои, перезапуск между записью причины и доставкой, потерю квитанции, явный повтор оператором, сохранение неуспешного запроса в истории, изоляцию участника/темы/источника, отказ провайдера и продолжение на границе вывода. Неопределенная отправка не повторяется автоматически.

Максимальная глубина и проверки увеличивают задержку. Например, арифметическая задача заняла 67,16 секунды вместо 17,54, рабочий план 221,44 вместо 120,21. Это единичные замеры, не оценка типичной производительности.

## Границы результата

Искусственные ограничения на шесть обменов и длину сохраненных сообщений сняты. История хранится полностью, в доступном окне передается целиком, после заполнения окна используется сохраняемая карта. Физическое окно модели конечно, сжатие не гарантирует сохранения каждого нюанса.

Максимум прямого API выбранной модели не равен всему комплексу Codex Desktop. Настройка ultra приложения, его инструменты и делегирование не включаются заменой одного API-параметра. В этих тестах выбрана прежняя gpt-6.1-sol, а не другая модель приложения.

Содержательные проверки охватывают описанные задачи. Они не гарантируют безошибочное выполнение любого будущего запроса. Семантическая проверка может оставить partial или needs_clarification, отказ провайдера сохраняется как отказ. Доставка реальному участнику после внедрения в рамках этой проверки не испытывалась.
