# Закрытые резервные копии и возврат данных

Этот раздел описывает приватные операции администратора. Файлы, полученные при восстановлении, не добавляют в GitHub и не прикрепляют к публичным issue. Программы восстанавливают из закрепленного полного релиза репозитория и проверяют по его манифестам. Официальная базовая ревизия Hermes остается `71d34bad1045610252eda02ee79549436896e784`, к ней применяются текущие патчи и расширения релиза от 24 ноября. Для прежних материалов и подписанных заданий нужен отдельный зашифрованный набор.

## Состав набора

| Часть | Что возвращает |
|---|---|
| daily/*.tar.zst.gpg | Профиль, сохраненные документы и главы, снимки SQLite, настройки, код локальных расширений и служебное состояние |
| db/ внутри архива | Согласованные снимки баз из /home/hermes/.hermes с относительными путями |
| sysdb/ внутри архива | Снимок базы квитанций и результатов из /var/lib/psy-recording-receipts |
| meta/media-manifest.tsv | SHA-256, размер и исходное приватное расположение каждой записи |
| media/<sha256>.gpg на внешнем узле | Зашифрованные файлы записей и результатов, без повторной передачи одинакового содержимого |
| Отдельно сохраненная парольная фраза | Возможность расшифровать набор даже после полной потери основного сервера |

Сохраните парольную фразу отдельно от основного сервера и копии. SSH-доступ отправителя и парольная фраза не должны попадать в публичный репозиторий. Доступ учетной записи хранилища ограничивается приемом резервных копий. IP нового отправителя должен быть разрешен. После удаления старой машины ее IP удаляют из этого разрешения.

## Установить ночное копирование

`ops/backup/psy-backup` соответствует рабочей процедуре: SQLite backup API под владельцем базы, отдельные снимки квитанций, шифрование AES256, проверка архива и SHA-256 медиа перед передачей. Базы копируются небольшими шагами с паузами, поэтому бот не ждет блокировку. База в режиме WAL копируется из одного снимка внутри транзакции чтения. Копия переводится в обычный режим журнала и не требует файлов -wal и -shm. Ночная проверка запускает тот же `tools/verify_backup.py`, что и восстановление, поэтому список обязательных файлов один. Записи отправляются по одной: проверка свободного места, шифрование, сверка SHA-256, передача и удаление временной копии. По воскресеньям так же заново предлагаются все записи, но на диске одновременно лежит не больше одной зашифрованной записи. Каталог на принимающем узле нельзя прочитать с основного, поэтому уже имеющиеся там копии не перезаписываются. Публичная версия получает адрес из закрытой настройки, а не из IP автора. При создании tar сохраняются также ACL и extended attributes. Для копий старого формата права восстанавливают отдельно.

На основном узле подготовьте пакеты gnupg, zstd, rsync, openssh-client и выполните:

```sh
sudo bash ops/install-backup
```

Установщик не запускает копирование. Заполните root-only destination.env в созданном каталоге конфигурации. Подготовьте в нем приватный SSH-ключ отправителя, проверенный known_hosts и файл парольной фразы. Они должны принадлежать root и иметь режим 600. Фраза вводится скрыто, ключ передается по защищенному каналу, значения не помещают в команды или журналы. Файл README.txt - публичная инструкция без секретов.

На принимающем узле нужны отдельная учетная запись, закрытый каталог и forced-command, разрешающий только rsync-запись в этот каталог. Используйте штатный rrsync с write-only ограничением и restrict/no-port-forwarding/no-agent-forwarding/no-pty. Не добавляйте этому ключу общий shell-доступ. Перед ограничением по from= проверьте фактический исходящий IP нового сервера.

После подготовки выполните одну настоящую копию. Сверьте на внешнем узле время, размер, права и открываемость. Затем включите таймер:

```sh
sudo systemctl start psy-backup.service
systemctl show psy-backup -p Result -p ExecMainStatus
sudo systemctl enable --now psy-backup.timer
```

Таймер по умолчанию работает около 04:30 по Москве с небольшим случайным сдвигом. Об ошибке сообщает независимая служба владельца. Она же сообщает, если последней успешной копии больше 26 часов. Код не удаляет старые внешние копии. Срок хранения и свободное место на принимающем узле контролируются отдельно. Ночная копия не обеспечивает RPO=0.

## Проверить архив без запуска Telegram

Получите выбранный зашифрованный архив на свободную машину через административный защищенный доступ. Write-only ключ основного сервера не предназначен для скачивания копий. Подготовьте отдельный закрытый каталог и пакет gnupg/zstd.

```sh
sudo install -d -m 0700 /var/tmp/psy-recovery
sudo python3 tools/verify_backup.py /var/tmp/psy-recovery/selected.tar.zst.gpg --passphrase-file /etc/psy-backup/passphrase
```

Проверка расшифровывает архив во временном закрытом каталоге, извлекает только обычные файлы, отклоняет выход за границы каталога и проверяет SQLite. Она не следует символическим и жестким ссылкам, не восстанавливает устройства, владельцев или привилегированные режимы. После проверки временная копия удаляется. Вывод содержит только счетчики и результат, без путей или текста материалов.

Для следующего этапа можно явно сохранить проверенные обычные файлы:

```sh
sudo python3 tools/verify_backup.py /var/tmp/psy-recovery/selected.tar.zst.gpg --passphrase-file /etc/psy-backup/passphrase --stage /var/tmp/psy-recovery/verified
```

Родитель staging-каталога должен быть закрытым, каталог verified еще не должен существовать. Эта операция также не запускает службы. Ссылки TLS не создаются, поэтому сертификат ниже настраивается отдельно.

## Вернуть состояние на свободный подготовленный узел

До копирования проверьте, что шлюз, worker, ASR, загрузчик, сокеты и таймеры выключены. Не извлекайте весь архив поверх нового корня. Используйте установленные из проверенного релиза программы, а не случайные старые unit-файлы из копии.

1. Верните данные из verified/home/hermes/.hermes в /home/hermes/.hermes. Код Hermes, его окружения и инструменты берутся из установленного релиза. Не используйте --new-profile для замены восстановленного SOUL.md.
2. Поверх восстановленных данных верните снимки из verified/db по тем же относительным путям внутри /home/hermes/.hermes. Например db/state.db заменяет /home/hermes/.hermes/state.db. Не копируйте db-notes.txt как базу. Удалите только соответствующие старые WAL/SHM пустого экземпляра, пока службы выключены.
3. Верните sysdb/var/lib/psy-recording-receipts/results.sqlite3 в /var/lib/psy-recording-receipts/results.sqlite3. Эта база принадлежит psy-deliver, группа psy-upload, режим 640. Профиль и обычные базы внутри домашнего каталога принадлежат hermes.
4. Верните исходный etc/psy-upload/recording-signing, root:root, режим 600. Подготовка хоста могла создать новый пустой ключ. Его заменяют восстановленным до первого старта. Ключи разных копий смешивать нельзя.
5. Верните состояние входа из auth.json, .env и связанные журналы в профиле, включая psy-owner-recovery. Верните var/lib/psy-codex-auth вместе с ним. Не берите более старый refresh token только потому, что он найден в другой копии. Шлюз, монитор и мост платформы должны обращаться к одному контроллеру продления, а не к независимым изменяемым копиям этого состояния. Если старый сервер после снимка продолжал продлевать вход, нужен его последний закрытый набор или новый вход владельца.
6. Для распознавания верните var/lib/psy-asr с checkpoint и сегментами под владельцем psy-asr, группой psy-deliver. Сводка progress доступна загрузчику на чтение через ACL. Это позволяет продолжить декодирование, если сами исходные байты тоже восстановлены.
7. Верните конфигурацию экземпляра из etc/psy/instance.env, проверьте ID и замените публичный адрес при смене машины. Сохраните root-владельца и права чтения hermes для не содержащих секретов настроек. Токены и OAuth остаются 600.
8. Выполните ops/stage-credential после восстановления .env. Служба Telegram использует тот же токен бота. Не перевыпускайте его только из-за смены сервера.

Все операции выполняются в закрытом каталоге. Не выводите содержимое конфигураций и дампы SQLite на экран. Для старого архива без ACL заново примените ограничения подготовленного узла к возвращенным данным. Внутри профиля владелец hermes, каталоги приватные. Очередь uploads имеет именованные права чтения/записи для psy-upload и psy-deliver. Медиа имеют права загрузчика на запись и psy-asr на чтение. У базы квитанций загрузчик имеет только чтение. Не исправляйте это общим chmod 777 или добавлением сервисов в группу hermes.

После возврата файлов выполните `sudo bash ops/restore-permissions` на выключенном экземпляре. Скрипт восстанавливает владельцев и ACL по именам, не запускает службы и отказывается работать при активных обработчиках или таймерах. Для каталогов общего доступа исходные правила задает ops/prepare-host. После возврата существующих файлов примените именованные ACL и к этим файлам, а не только default ACL каталога. Контрольные проверки ops/test-host и ops/verify-ready должны пройти до старта. Числовые UID источника не копируют в зависимости systemd, install-runtime подставляет текущий UID.

## Вернуть большие файлы

Каждая строка meta/media-manifest.tsv связывает SHA-256, число байтов и приватный путь. Для каждого пути восстановите соответствующий media/<sha256>.gpg. Расшифровывайте в новый временный файл внутри закрытого каталога, сверяйте число байтов и SHA-256, затем переносите в /home/hermes/.hermes/media-vault/uploads. Допустимы только пути внутри этого корня, без .., символических ссылок и произвольных системных назначений. Одинаковый хеш может соответствовать нескольким файлам.

Эти шаги выполняет `tools/restore_media.py`. Скачайте нужные media/<sha256>.gpg через административный доступ в закрытый каталог, например /var/tmp/psy-recovery/media. Манифест берется из каталога verified, подготовленного `verify_backup.py --stage`. Службы должны быть выключены.

```sh
sudo python3 tools/restore_media.py --manifest /var/tmp/psy-recovery/verified/meta/media-manifest.tsv --encrypted /var/tmp/psy-recovery/media --passphrase-file /etc/psy-backup/passphrase --target /home/hermes/.hermes/media-vault/uploads
sudo bash ops/restore-permissions
```

Скрипт принимает только пути ниже корня uploads, не следует по ссылкам и не перезаписывает существующие файлы. Каждая запись расшифровывается в новый временный файл рядом с местом назначения, сверяется по размеру и SHA-256 и только потом получает свое имя с режимом 600. Совпадающий существующий файл засчитывается как already_present, отличающийся - как conflicting и остается без изменений. Вывод содержит только счетчики и хеши отсутствующих копий, без путей. При отсутствии копий, ошибке проверки или конфликте код возврата ненулевой. Повторный запуск продолжает с того же места.

GitHub CI на чистой машине запускает установленный psy-backup в песочнице его unit с локальным каталогом вместо внешнего узла. Второй запуск идет по воскресному пути. Затем CI проверяет архив через verify_backup.py и возвращает записи через restore_media.py со сверкой байтов: `ops/tests/test_backup_roundtrip.sh`.

Возвращайте также TXT и служебные сегменты из манифеста, если они там есть. После копирования верните владельцев и ACL. Одного архива daily недостаточно для исходных записей, которые вынесены в media. Проверка только наличия файла без контрольной суммы недостаточна.

## Проверить и переключить

Продолжите с раздела HTTPS в [RESTORE.md](RESTORE.md). Не переносите весь старый /etc/letsencrypt поверх действующей установки. Для нового адреса получите действующий сертификат с согласованным именем линии. Таймер продления должен зависеть только от работающего адреса, а не от IP удаленной машины.

Проверьте целостность всех SQLite, наличие документов и исходного большого аудио, соответствие квитанций подписанным заданиям, незавершенные отправки, права и фактический ответ модели. Состояние sending/unknown нельзя автоматически пересылать повторно без проверки доставки. Готовые главы сохраняются в базе группы и используются при продолжении, пока эта база возвращена целиком.

После успешной приемки сделайте новую внешнюю копию. Удалите временные расшифрованные файлы и убедитесь, что они не попали в Git. Сохраненная проверка архива доказывает открываемость этого набора. Полное время восстановления с нуля и отсутствие потерь при любой аварии требуют отдельного учения и здесь не обещаются.

## Сохранить результат исправлений от 24 ноября

Программы восстановления должны включать исправленные точки входа Hermes, `hermes_cli/psy_gateway_exit.py`, актуальный монитор и общий модуль проверок. Одного сохраненного профиля недостаточно, чтобы вернуть это поведение. Полный набор программ проверяется текущими `gateway/manifest.json`, `gateway/group-manifest.json` и общим инвентарем `ops/inventory.json`.

Готовые главы и признаки их завершения возвращаются вместе. Финальная защита выхода включается после успешной настоящей `stop_task`, а не по раннему событию остановки. Она не ограничивает общую длительность лекции. Не заменяйте контроль сохранения простым увеличением `TimeoutStopSec`.

После восстановления проверьте [40 проверок надежности и 2 изолированных примера](TESTS.md). Для них используются отдельные базы, искусственная запись и локальный Telegram-приемник. Реальный модельный пример сохраняет единственного владельца действующего OAuth. Учетные данные в GitHub Actions для такого прогона не загружают.

В публичную историю не должны попасть расшифрованные архивы, дампы SQLite, логи с перепиской, файлы ключей, действующие ID участников или исходные записи. Разрешенные примеры используют вымышленные идентификаторы и сгенерированную речь. Сохраняйте итоговые счетчики и SHA-256 отдельно от закрытого набора.

Мост платформы использует тот же актуальный контроллер Codex. Копия ПСИ не является копией пользовательских данных соседней платформы. Если требуется восстановить обе системы, отдельно проверьте состав данных платформы, ее health endpoint и доступ к общему мосту, не создавая второе продление одного входа.
