# Независимые уведомления владельцу

В рабочей схеме 2 уровня контроля. На основном узле psy-alerts проверяет состояние и перезапуски служб, результаты проверок шлюза и загрузки, таймеры, давность резервной копии, доступную память и давление памяти, срок сертификата. Готовность шлюза сверяется по текущему PID и состоянию Telegram `connected`. На отдельном существующем узле тот же модуль проверяет публичный HTTPS адрес снаружи. Оба пути отправляют только личное уведомление положительному Telegram ID владельца. В группу сообщения мониторинга не отправляются.

Работающий внешний наблюдатель не переносится на основной сервер: при потере основной машины уведомление должно прийти с другого узла. Для этого второму узлу нужен отдельно разрешенный доступ к учетным данным Telegram. Не публикуйте его конфигурацию.

## Как приходят уведомления

Одна проверка отправляет не больше одного сообщения-сводки. В нем 3 раздела: новые проблемы, проблемы без изменений и проблемы, которых больше нет. Напоминание о неустраненной проблеме приходит через 1 час, затем через 3 часа, затем раз в 6 часов. Проблема считается устраненной после 3 проверок подряд без нее. Разовое событие, например автоматический перезапуск службы, сообщается один раз и не получает отдельного сообщения об устранении. В час уходит не больше 4 сообщений. Отложенные пункты попадают в следующую сводку.

Кроме служб основной узел проверяет, что таймеры включены и недавно запускались, что последняя успешная резервная копия моложе 26 часов и что локальный архив vault работает. Токен бота берется из закрытого `/etc/psy-upload/telegram` через LoadCredential, при его отсутствии из `.env` профиля. Сбой отправки записывается в журнал только с HTTP-кодом, без адреса и токена. После 3 неудачных отправок подряд служба psy-alerts завершается с ошибкой и видна в `systemctl --failed`, а первое доставленное после этого сообщение сообщает число неудачных попыток. psy-healthcheck завершается с ошибкой, если psy-alerts не выполнял проверку больше 10 минут. Это сразу запускает внеочередную проверку.

Каждая наблюдаемая служба при сбое запускает свой экземпляр `psy-alert@<служба>.service`. Раньше все службы указывали в OnFailure= одну и ту же psy-alerts.service, и systemd при каждом ее запуске записывал в журнал предупреждение о нескольких источниках сбоя.

## Подготовить внешний узел

Установите проверенные исходники и Python 3.12. На втором узле выполните:

```sh
sudo bash ops/install-observer
```

Установщик копирует psy_alerts.py, общий модуль /usr/local/lib/psy-common/psy_common.py, без которого psy_alerts.py не запускается, и unit-файлы, создает закрытый шаблон. При обновлении узла снова запустите install-observer, а не копируйте один psy_alerts.py. Он не включает таймер и не отправляет сообщения. В /etc/psy-observer/instance.env заполните положительный ID владельца и актуальный PSY_PUBLIC_URL. Затем сохраните прежний токен бота через скрытый ввод:

```sh
sudo python3 ops/stage-observer.py
```

Конфигурация принадлежит root и имеет права 600. Скрипт не создает нового Telegram-бота и не продлевает Codex. Для внешней проверки ключи OAuth не нужны.

До первого включения выполните read-only проверку в окружении службы:

```sh
sudo bash -c 'set -a; . /etc/psy-observer/instance.env; set +a; python3 -I /usr/local/libexec/psy-alerts.py --remote --check-only'
sudo systemctl enable --now psy-alerts.timer
```

При разрешенной проверке личных уведомлений используйте --test-notice вместо --check-only. Это отправляет сообщение только владельцу. Для проверки работы агента в группе уведомление мониторинга не подходит.

## После смены адреса

Одновременно обновите PSY_PUBLIC_URL на основном и внешнем узлах. В действующем старом экземпляре также может быть PSY_UPLOAD_URL, его значение должно совпадать. Перезапустите только oneshot-проверку, чтобы не принять уже идущий старый запрос за результат новой настройки. Проверьте /healthz с внешней машины и дождитесь следующего срабатывания таймера.

При постоянном отказе HTTPS внешний наблюдатель уведомляет владельца после 3 последовательных проверок. Это свидетельство доступности мини-апки. Оно не подтверждает ответ модели, целостность архива или появление TXT на телефоне участника. Эти проверки выполняются отдельно.

В текущем [psy_alerts.py](../ops/libexec/psy_alerts.py) сохранена функция `group_status`, читающая `vault/group-psy/group.sqlite3`. Она сообщает о старых заданиях без отметки прогресса, неопределенной доставке, ошибках и сохраненных попытках повтора. Отсутствие этой БД или устойчивый сбой ее чтения также вызывает предупреждение. Эта проверка относится к сохраненным заданиям отключенного обработчика. Новые запросы выполняет штатный Hermes, и их продвижение по этой БД определить нельзя. `psy-alerts` сам не возобновляет генерацию и не повторяет запросы к модели.

## Исходное состояние и диагностика конкретного ответа

Перед обновлением работающего экземпляра выполните из подготовленного релиза:

```sh
sudo python3 -B ops/capture_state.py
```

Скрипт сохраняет полные версии групповых модулей, их зависимостей Hermes, config.yaml и SOUL.md от пользователя hermes в закрытом каталоге vault/group-psy/runtime-snapshots. Параметры экземпляра, маркер установленного релиза и состав unit службы сохраняются отдельно в root-каталоге /var/lib/psy-deploy/baseline-*. Для каждого файла проверяется SHA256. На экран попадают только хеши, пути и признак проверки. Секреты, личные инструкции и переписка не выводятся. Исходники закрепленного Hermes и полный пакет релиза сохраняются по обычной процедуре обновления.

Снимок фиксирует файлы и настройки перед обновлением. Автоматическая привязка каждого нового ответа Hermes к прежнему групповому аудиту не выполняется. Сохраненные снимки и материалы в `vault` остаются на месте.

Для диагностики нового ответа используйте журнал `hermes-gateway.service`, журнал профиля `logs/gateway.log`, текущий PID и состояние подключения Telegram. История разговора хранится в штатной сессии Hermes в `state.db`. В публичный отчет включайте только технические статусы и обезличенные сведения. Журналы и БД могут содержать переписку и не предназначены для публикации целиком. Подключение `connected` подтверждает готовность транспорта, но не качество конкретного ответа или прочтение сообщения.

## Контекст и параметры штатного Hermes

Рабочий профиль `/home/hermes/.hermes` использует провайдер `openai-codex` и модель `gpt-6.1-sol`. Вход остается через подписку ChatGPT, платный API и запасной провайдер не подключаются. Глубина рассуждения определяется настройками штатного Hermes и возможностями модели. Прежнее правило отдельного группового клиента о принудительном `max` к этому маршруту не применяется.

После проверки числовых ID группы и отправителя исходное сообщение, вложения и цепочка ответов передаются штатному Hermes. Он ведет разговор в своей сессии в `/home/hermes/.hermes/state.db` и использует обычные инструменты файлов, терминала и поиска. Дополнительного переписывания запроса или обрезки сообщений отдельным групповым обработчиком нет.

Штатное сжатие контекста включено: `compression.enabled=true`, `compression.threshold=0.5` (50%). Отдельный токенизатор прежнего обработчика для этого маршрута не требуется. Сжатие выполняет сам Hermes в пределах окна модели. Перед изменением `state.db` нужна согласованная SQLite-копия с учетом WAL, проверка изменений на копии и сохраненный путь отката.

Новые результаты сохраняются в `/home/hermes/.hermes/outputs`, владелец `hermes`, права `0700`. Каталог входит в действующий бэкап профиля. Штатный файловый инструмент Hermes запрещает запись в `vault`, старые материалы и `vault/group-psy/runtime-snapshots` не удаляются и не переносятся. Служба продолжает работать от `hermes` без sudo с существующим `privacy.conf`.
