# Восстановление PSY на новом сервере

Инструкция дополнена 25 ноября 2026 года отдельной установкой токенизатора длинной истории. Базовый официальный commit Hermes остается `71d34bad1045610252eda02ee79549436896e784`, а текущие расширения, патчи и общий модуль проверяются манифестами релиза. Рабочая схема: один основной сервер с Hermes, Mini App, офлайн-распознавателем и отправкой результатов. Отдельный существующий узел хранит зашифрованные копии и проверяет доступность основного. Постоянный промежуточный сервер для прежнего IP не требуется.

Есть 2 варианта восстановления. Для нового бота используйте пустой профиль и новый вход. Для прежнего бота сначала верните закрытые данные, ключи подписанных загрузок и состояние OAuth из актуальной копии. Новый вход и новый ключ подписания поверх восстановленных данных создавать не следует.

## Подготовить свободную машину

Команды рассчитаны на Ubuntu 24.04 x86-64, systemd, ядро 6.8+ и POSIX ACL. Память, CPU и диск подбирают по текущей нагрузке. Шлюз работает от hermes, остальные компоненты имеют отдельные системные учетные записи.

1. Получите проверенный релиз этого репозитория в `/opt/psy-source`. Каталог принадлежит администратору и недоступен сервисам на запись. Сохраните SHA релиза.
2. Установите зависимости и подготовьте учетные записи. Скрипты подготовки не запускают службы.

```sh
sudo apt-get update
sudo apt-get install -y acl ca-certificates curl ffmpeg git gnupg libgomp1 libseccomp2 openssh-client poppler-utils python3-venv rsync util-linux zstd
cd /opt/psy-source
sudo bash ops/prepare-host
```

Не выполняйте установку поверх работающего экземпляра. Если прежний сервер доступен, финальная синхронизация данных проводится после завершения активных заданий и остановки старого шлюза, работников и таймеров авторизации. У Telegram должен быть один потребитель обновлений, у Codex - один владелец текущего состояния входа.

## Установить программы без запуска бота

Версия Hermes закреплена на официальном коммите `71d34bad1045610252eda02ee79549436896e784`. URL установщика и аргумент установки указывают один и тот же коммит. Факультативные браузерные компоненты можно пропустить.

```sh
sudo -u hermes -H bash <<'INSTALL'
set -eu
cd /home/hermes
ref=71d34bad1045610252eda02ee79549436896e784
script=$(mktemp)
trap 'rm -f "$script"' EXIT
curl -fsSL "https://raw.githubusercontent.com/NousResearch/hermes-agent/$ref/scripts/install.sh" -o "$script"
bash "$script" --commit "$ref" --hermes-home /home/hermes/.hermes --dir /home/hermes/.hermes/hermes-agent --non-interactive --skip-browser --skip-computer-use
INSTALL
sudo -u hermes -H python3 gateway/apply.py apply /home/hermes/.hermes/hermes-agent
sudo -u hermes -H python3 gateway/apply.py verify /home/hermes/.hermes/hermes-agent
```

Установите зависимости Hermes, 2 среды Python загрузчика и распознавателя и проверенную модель Whisper по [ops/README.md](../ops/README.md) и [media/README.md](../media/README.md). Контрольные суммы 4 файлов модели находятся в `media/model.sha256`. После определения действующего Python Hermes обязательно установите отдельный токенизатор по разделу ниже. Установка основных служб автоматически его не собирает.

Для прежнего бота установите runtime без перезаписи профиля:

```sh
sudo bash ops/install-runtime
```

Для нового бота с пустым хранилищем используйте `sudo bash ops/install-runtime --new-profile`. Не используйте этот флаг для замены восстановленного личного SOUL.md. `install-runtime` сам определяет новый Linux UID hermes для зависимости `user@UID.service`. Переносить числовой UID старой машины в unit-файл нельзя.

## Проверить пакетную среду Hermes

В проверенном экземпляре от 25 ноября launcher `.hermes/bin/hermes` использует упакованный Python 3.14.7 и выбранное окружение зависимостей. Наличие launcher не означает наличие соседнего `.hermes/bin/python` или прежнего `.venv/bin/python`. Для работающего процесса определяйте интерпретатор через `systemctl show hermes-gateway.service -p MainPID -p ExecStart` и `/proc/<MainPID>/exe`. Для остановленного экземпляра читайте выбранную среду через `committed_venv()` и `venv_python()` от пользователя `hermes`, как показано в [инструкции установки токенизатора](../ops/README.md#локальный-токенизатор-для-длинной-истории).

Установку закрепленного Hermes и синхронизацию его зависимостей выполняйте по [ops/README.md](../ops/README.md). Загрузчик и офлайн-распознаватель используют свои отдельные среды Python 3.12. Их зависимости закреплены в `media/requirements.lock.txt` и `media/asr-requirements.lock.txt`, модель - в `media/model.sha256`. Не меняйте активное окружение работающей службы ради приемочного теста.

Для обычных команд используйте установленный launcher. Для изолированных примеров определяйте интерпретатор выбранной среды по [TESTS.md](TESTS.md). Пример группового ответа читает `committed_venv()` и `site_packages()` без запуска обновления. Полный `hermes_bootstrap` способен подготовить обновление при импорте, поэтому тест не использует его как средство подключения библиотек.

Текущий релиз включает исправленные `gateway/run.py`, `hermes_cli/gateway.py` и `hermes_cli/psy_gateway_exit.py`. Перед запуском проверьте весь `gateway/manifest.json`, `gateway/group-manifest.json` и общие файлы, а не только наличие нового модуля.

## Установить токенизатор длинной истории

Этот шаг обязателен перед приемкой длинной памяти. Среды загрузчика и распознавателя на Python 3.12 не определяют ABI шлюза. Сначала получите `psy_runtime_python` для фактической пакетной среды Hermes по [ops/README.md](../ops/README.md#локальный-токенизатор-для-длинной-истории), затем выполните из проверенного репозитория:

```sh
sudo /usr/bin/python3.12 ops/install-context-tokenizer \
  --python /usr/bin/python3.12 \
  --runtime-user hermes \
  --runtime-python "$psy_runtime_python"
```

Системный CPython 3.12, принадлежащий root, служит только доверенной средой подготовки. Установщик выполняет фактический Python Hermes исключительно от `hermes`, сверяет его ABI и проверяет кодировку без сети. Зависимости устанавливаются отдельно, пакетная среда Hermes не меняется. Версии и хеши закреплены в `ops/context-tokenizer/requirements.lock.txt`.

Указатель `/opt/psy-context-tokenizer/current` должен вести на проверенный выпуск внутри `/opt/psy-context-tokenizer/releases`. Выпуск содержит пакеты нужного Python, кеш `o200k_base`, manifest и lock-файл. Не переносите только указатель без каталога назначения и не используйте выпуск для другого ABI. При смене Python повторите установку. Подключение пакетов идет внутри процесса, отдельная служба или исполняемый `venv/bin/python` токенизатору не нужны.

После восстановления проверяйте `tokenizer.available=true` и `tokenizer.estimator=o200k_base` в изолированном содержательном примере, запущенном настоящим Python Hermes. Резервная оценка по байтам UTF-8 не заменяет этот критерий. Локальная проверка токенизатора не обращается к модели или Telegram, а результат сжатия истории требует отдельной содержательной проверки.

## Вернуть закрытые данные прежнего бота

Для этой ветки выполните [docs/RECOVERY.md](RECOVERY.md) до авторизации и до первого старта. Публичный GitHub хранит программы и шаблоны. Диалоги, документы, главы, аудио, OAuth и ключи подписания восстанавливаются из отдельного зашифрованного набора.

Критические правила:

- Состояние OAuth, credential pool, журналы незавершенного обмена и восстановления записи возвращаются вместе. Поздняя копия с новым ключом имеет приоритет над ранней. Шлюз, контрольный таймер и мост платформы должны использовать один контроллер продления. Вторую изменяемую копию того же разрешения для платформы не создают.
- Восстанавливается исходный `recording-signing`. Без него существующие билеты, задания, сеансы и квитанции перестанут проходить проверку.
- Очередь загрузки и база результатов работника восстанавливаются совместно с медиа. SQLite берется из каталогов согласованных снимков `db/` и `sysdb/`, а не из случайно скопированного живого файла.
- Возвращаются владельцы и ACL по именам учетных записей. Режим 600 для OAuth и токенов сохраняется. Числовые UID новой машины могут отличаться.
- Готовые главы и сегменты расшифровки сохраняются вместе с их состоянием. Перед повторной отправкой записи с неопределенным результатом нужна проверка факта доставки.

Для восстановленного действующего OAuth новый device-code не требуется, пока проверка не покажет необходимость повторного входа. Для восстановленного токена скрытый ввод пропускается. `ops/stage-credential` извлекает существующий токен в root-only credential без вывода значения.

## Настроить экземпляр, Codex и HTTPS

Заполните `/etc/psy/instance.env` по образцу `ops/instance.env.example`. Потребуются ID владельца, группы и бота, имя бота и один актуальный публичный HTTPS origin Mini App. В этом файле нет токена или OAuth. Публичные модули получают адрес из `PSY_PUBLIC_URL`. При восстановлении старой конфигурации с `PSY_UPLOAD_URL` приведите его к тому же значению. Не оставляйте разные адреса у загрузчика, шлюза и мониторинга.

Для нового экземпляра добавьте токен через скрытый ввод и настройте профиль по [gateway/README.md](../gateway/README.md). Для прежнего проверьте восстановленные ID и профиль, не подменяя их демонстрационными значениями. Службы читают конфигурацию через EnvironmentFile, включая сокетные брокеры и проверку загрузчика.

```sh
sudo bash ops/stage-credential
```

Для нового входа используйте только `openai-codex` через ChatGPT OAuth/device-code. Команды выполняются от hermes с HERMES_HOME=/home/hermes/.hermes. Проверка: `hermes auth list`, `model.provider=openai-codex` и короткий one-shot. Не добавляйте OPENAI_API_KEY, OpenRouter или альтернативного провайдера при ошибке.

Настройте прямой доступ к новому серверу: TCP 80 для ACME и порт Mini App, по умолчанию 9443. Получите сертификат для адреса из `PSY_PUBLIC_URL`. Полные команды для DNS и IP есть в [ops/README.md](../ops/README.md). Рабочее имя линии Certbot после переноса - `psy-upload-ip`. Оно согласовано с deploy hook и таймером в этом репозитории. Если закрытая копия содержит другую линию, согласуйте все 3 места до старта.

```sh
sudo /usr/local/libexec/psy-upload-deploy-cert --stage
sudo bash ops/verify-ready
```

Не переносите старые Node/Python окружения как обязательный способ установки. Их собирают из зафиксированных зависимостей. Не восстанавливайте архив целиком поверх /etc и новых unit-файлов.

## Сохранить знакомую кнопку "Записи"

При прежнем имени бота групповая кнопка использует ссылку `https://t.me/<имя_бота>?startapp=psy_group`. Ее можно оставить в прежнем закрепе при смене сервера.

1. В BotFather обновите Main Mini App URL на новый HTTPS origin.
2. Обновите глобальное меню бота и индивидуальное меню владельца. Telegram допускает индивидуальную настройку, которая имеет приоритет над общей.
3. Оставьте неизменным существующий групповой закреп, если он указывает на тот же startapp. Не создавайте второй закреп только из-за смены IP.
4. Измените адрес внешнего наблюдателя на втором узле.

Без отправки в чаты можно выполнить:

```sh
sudo bash <<'CHECK'
set -eu
set -a
. /etc/psy/instance.env
set +a
export CREDENTIALS_DIRECTORY=/etc/psy-upload
python3 /opt/psy-source/tools/telegram_entry.py check
CHECK
```

`check` ничего не публикует. `install` меняет меню и при необходимости публикует/закрепляет сообщение в группе. Используйте `install` только при разрешенной публикации. При восстановлении существующей кнопки сначала проверяйте и обновляйте меню, не отправляя новое сообщение.

## Включить и принять восстановленный экземпляр

Запускайте сокеты, ASR, загрузчик и работника, затем шлюз. После `connected` включайте таймеры. Порядок и команды находятся в [ops/README.md](../ops/README.md).

Проверьте:

- `hermes --version`, `hermes auth list`, провайдера и короткий реальный one-shot через подписку.
- `systemctl is-active` и `systemctl is-enabled` для hermes-gateway, psy-upload, psy-upload-worker, psy-asr.
- HTTPS `/healthz` с внешнего узла. Без авторизации `/api/jobs` должен возвращать 401.
- Настоящую кнопку в Telegram и файл больше 20 МБ. Проверяйте полный файл, контрольную сумму, распознавание и появление TXT в выбранном чате.
- Если в группу писать запрещено, выполните оба изолированных примера из [TESTS.md](TESTS.md). Они проверяют настоящий Codex и распознавание с локальным Telegram-приемником. Для них не требуется сообщение в личку или группу. Появление результата на телефоне участника требует отдельного разрешенного рабочего события.
- Согласованность баз и приватных медиа из закрытой копии, SQLite integrity_check, владельцев и права доступа. Достаточно счетчиков и контрольных сумм, содержимое материалов не выводится.
- Сухой прогон продления сертификата уже только для нового адреса, независимый мониторинг и получение зашифрованной копии на внешнем узле.

Только после этих проверок завершайте использование старого узла. Дождитесь окончания открытых загрузок, проверьте отсутствие зависимостей от старого адреса, сохраните свежую копию. Если цель - прекратить оплату старой машины, ее удаляют после приемки, а не просто выключают. Восстановление входа из устаревшего состояния и одновременный старт двух шлюзов недопустимы.

Автоматический перезапуск и сохранение этапов не доказывают отсутствие потерь при любой аварии. Гарантии RPO=0 и полного восстановления за 5 минут эта инструкция не заявляет.

## Проверить исправления завершения и уведомлений

Текущий релиз различает выполнение задания и финальный выход процесса. Защита выхода включается только после успешного завершения настоящей `stop_task`, сохранения состояния и закрытия баз. Одного `_shutdown_event` недостаточно: в базовом коде он устанавливается раньше окончания записи.

12 секунд финального завершения и отдельная защита еще на 2 секунды покрывают зависшие фоновые задачи, executor и хвост очистки. До безопасной точки таймер не работает. Общая длительность лекции и глубокого разбора этим исправлением не ограничивается.

Монитор дает 120 секунд переходным состояниям запуска, остановки и перезагрузки настроек. Настоящие `failed` и `inactive` без ожидающей systemd-задачи продолжают вызывать тревогу сразу. Восстановление шлюза подтверждается текущим PID и Telegram `connected`. После уже отправленной тревоги уведомление о восстановлении проходит вне общего часового лимита напоминаний. Настоящий `retry_after` Telegram сохраняет приоритет, успешная повторная проверка дубль не создает.

Запустите 40 проверок надежности по [TESTS.md](TESTS.md), затем проведите разрешенный перезапуск только при простое. Проверяйте не только новый `active`, но и фактическое завершение старого процесса без принудительного убийства по прежнему 70-секундному пределу. Не воспроизводите сбой на рабочей лекции.

## Обновить уже работающий экземпляр

`ops/install-runtime` предназначен для остановленного узла. Работающий ПСИ обновляют из проверенной копии репозитория штатным инструментом:

```sh
sudo python3 ops/update_live.py plan
sudo python3 ops/update_live.py apply
```

`plan` показывает состав изменений без применения. `apply` проверяет известную базу и манифесты, сохраняет предыдущие программы и согласованные копии баз, запускает preflight и перезапускает затронутые службы. Подробности и откат находятся в [ops/README.md](../ops/README.md#обновление-работающего-узла).

При активном групповом задании или распознавании применение откладывают. Отказ из-за занятости не обходят принуждением. Перед повторной попыткой снова проверьте обе очереди и штатную работу шлюза. Нулевого `active_agents` недостаточно для пользовательской групповой очереди.

Если используется отдельная процедура с `worker.lock`, блокировку удерживают от повторной проверки простоя до готовности нового процесса. Пока она удерживается, новые групповые запросы сохраняются в очереди и ждут. Не применяйте ручную смену файлов или принудительный перезапуск вместо штатной процедуры.

Откат программы не должен возвращать устаревший OAuth или старую копию рабочих баз поверх более поздней работы. Если после успешного переключения появился новый запрос, отложите повторный тест, не перезапускайте занятую службу ради записи отчета.

## Проверить соседнюю платформу

Если используется платформа через `psy-platform-bridge`, установите ее соединение с мостом по [ops/README.md](../ops/README.md#мост-для-соседней-платформы). Сокет и проверка `SO_PEERCRED` должны допускать только назначенную учетную запись. Второй вход в ту же подписку не создается.

Проверка моста без модельного запроса и отправки сообщений:

```sh
sudo curl --fail --silent --show-error --unix-socket /run/psy-platform-bridge.sock 'http://x/health?deep=1'
```

Ожидается `ok=true`, `codex=ready`. Это подтверждает доступность общего входа, а не новый ответ модели или работу всех пользовательских сценариев платформы.

Отдельно проверьте ее публичный health endpoint, например `https://platform.example.invalid/api/healthz`, интерфейс и журналы. Адрес примера заменяется настройкой восстановленного экземпляра. HTTP 200 у health endpoint не доказывает успешный вход пользователя и выполнение его задачи. Восстановление и данные платформы имеют собственную границу и не заменяются резервной копией ПСИ.
